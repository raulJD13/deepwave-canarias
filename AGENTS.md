## 1. Project overview

**DeepWave Canarias** is a maritime forecasting and risk-support system for coastal areas of the Canary Islands.

The project uses oceanographic, meteorological and coastal/geographic data to anticipate sea conditions and transform physical predictions into operational information for:

- beach safety
- swimmers and tourists
- lifeguards and municipal services
- surfers and surf schools
- light recreational navigation
- coastal tourism companies

The system is not just a measurement dashboard. It is designed to **anticipate future maritime risk** before it happens.

Main forecast horizons:

```text
+3h, +6h, +12h, +24h, +48h
```

Main physical predictions:

```text
hs                      significant wave height
tm02                    mean wave period
tp                      peak wave period, secondary target
swell_height
swell_period
wave_direction
swell_direction
wind_speed
wind_direction
sea_level
daily_tidal_range
```

Derived operational modules:

```text
risk_general            general maritime risk
risk_beach              beach/swimmer risk
risk_navigation         light-navigation risk
surf_score              0-10 surf quality score
surf_quality            poor / fair / good / very_good / epic
```

Important disclaimer:

```text
DeepWave Canarias is a complementary decision-support tool.
It does not replace official maritime, meteorological, lifeguard or emergency warnings.
```

## 3. Final modeling architecture

The selected final architecture is:

```text
LightGBM physical forecasts
→ interpretable physical risk rules
→ interpretable surf score rules
```

### 3.1 Physical model

Final main model family:

```text
LightGBMRegressor per target and horizon
```

Directional variables are handled through sine/cosine components and reconstructed to degrees.

Strong physical targets:

```text
hs
tm02
swell_height
swell_period
wave_direction
wind_speed
wind_direction
sea_level
daily_tidal_range
```

Secondary targets:

```text
tp
swell_direction
wind_wave_height
```

Not-priority or experimental targets:

```text
sea_surface_salinity
current_speed
sea_surface_temperature
current_direction
```

Known final performance highlights for `hs`:

```text
MAE hs +24h ≈ 0.3159 m
MAE hs +48h ≈ 0.4432 m
```

### 3.2 Risk architecture

Final risk logic:

```text
predicted physical variables → risk rules
```

Risk modules:

```text
risk_general
risk_beach
risk_navigation
```

The project evaluated direct classifiers, persistence baselines and physical-derived risk. The final preference is **physical-derived risk** for interpretability, with persistence used as a strong long-horizon baseline in some modules.

### 3.3 Surf architecture

Final surf logic:

```text
predicted hs + period + wind + direction + coast orientation → surf_score
```

Final preferred module:

```text
PhysicalDerivedSurfScore
```

`DirectLGBMSurfScore` exists only as an experimental comparison. It should not become the main final production module unless the user explicitly asks.

### 8.1 Response design

API responses should be predictable and frontend-friendly.

A forecast record should include:

```json
{
  "zona_id": "string",
  "zone_name": "string",
  "isla": "string",
  "base_time": "datetime",
  "valid_time": "datetime",
  "horizon_hours": 24,
  "physical": {
    "hs": 1.23,
    "tm02": 7.8,
    "period": 7.8,
    "wind_speed": 8.4,
    "wind_direction": 45.0,
    "wave_direction": 320.0,
    "sea_level": 0.2
  },
  "risk_general": {
    "level": 1,
    "label": "moderate",
    "label_es": "medio",
    "color": "#f1c40f"
  },
  "risk_beach": {},
  "risk_navigation": {},
  "surf": {
    "score": 6.3,
    "quality": "very_good",
    "quality_es": "muy bueno",
    "color": "#3498db"
  },
  "recommendation": "..."
}
```

### 8.2 Backend behavior

The API must:

- load JSON once on startup or lazily with caching
- never crash on missing optional fields
- return 404 for unknown `zona_id`
- return 400/422 for unsupported horizon
- include CORS for local frontend development
- expose Swagger automatically at `/docs`
- keep responses JSON serializable
- keep startup lightweight

Recommended local command:

```bash
uvicorn src.api.main:app --reload --host 127.0.0.1 --port 8000
```

## 13. Domain and safety constraints

This is a maritime decision-support tool. Treat outputs responsibly.

Always preserve this idea in UI/API/docs:

```text
DeepWave Canarias is complementary and does not replace official warnings.
```

Do not phrase recommendations as absolute safety guarantees.

Use wording like:

```text
"Se recomienda precaución..."
"Consultar avisos oficiales..."
"Condiciones previstas..."
"Herramienta complementaria..."
```

Avoid wording like:

```text
"Seguro para bañarse"
"Puedes navegar sin riesgo"
"Predicción garantizada"
```

Risk and surf labels are derived from physical rules, not from official incident records.

## 14. Coding standards

General:

- Write clear, maintainable code.
- Prefer small functions and explicit names.
- Keep Spanish user-facing labels where appropriate.
- Keep code comments concise and useful.
- Avoid overengineering.
- Avoid hidden network calls.
- Avoid global mutable state unless it is a cached app-data object.
- Do not add secrets or tokens.

Python:

- Use type hints when practical.
- Use `Path` instead of hard-coded string paths.
- Use Pydantic models for API responses.
- Keep JSON loading centralized in `services.py`.
- Return structured errors.

JavaScript:

- Use modular functions.
- Keep API URL configurable.
- Handle loading/error states.
- Do not assume every field is present.
- Format null values as `—`.

CSS:

- Clean dashboard style.
- Responsive layout.
- Use accessible color contrast.
- Keep risk colors consistent with `app_data/risk_legend.json`.

## 18. Acceptance criteria for the production phase

The production phase is considered successful when:

- `app_data/` exists and validates
- `uvicorn src.api.main:app --reload` starts without errors
- Swagger works at `/docs`
- `/health` returns OK
- `/zones` returns zones
- `/predict/{zona_id}` returns a full forecast
- `/predict/all?horizon=24` returns map-ready data
- `/risk/{zona_id}` returns risk modules
- `/surf/{zona_id}` returns surf score
- frontend loads in browser
- frontend shows map/cards/charts
- Docker starts the backend
- tests pass with `pytest -q`
- no heavy data/model files are committed
